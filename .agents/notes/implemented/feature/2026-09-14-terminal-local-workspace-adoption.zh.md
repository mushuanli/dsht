# Agent Note：在已注册工作区目录里启动会跳过工作区选择

Status: implemented

## Problem

客户端总是停在选择工作区这一屏，即使它就是在宿主已经注册过的目录里启动的。在项目里运行 `dsht`，"用哪个工作区"这个问题其实已经由当前目录回答了，于是每个会话的第一件事就是多按一次确认键；而那个目录若在宿主里以别的名字注册，列表反而不好认。

## Decision

`SessionController.adoptLocalWorkspace(directory)` 把客户端工作目录与已注册的工作区路径做匹配并采用最合适的那个，`Controller.ready()` 在第一次拉取列表之后、读者被迫选择之前调用它。匹配按**完整路径分段**进行——目录必须等于某个工作区路径，或以"该路径 + 分隔符"开头，反斜杠先归一化——因此 `/srv/app-old` 不会匹配 `/srv/app`；最长匹配优先，嵌套在另一个工作区里的那个胜出。采用即调用既有的 `pickWorkspace`，于是屏幕变为会话列表、状态行写明 `Workspace from this directory · ← to switch`，而列表里的 `←` 仍然回到工作区选择器。

只有命令行没有指定会话时才走这条捷径，因此 `--session` 照旧直接打开。其余行为不变：宿主路径与客户端路径不同的情况（远端宿主的常态）不会匹配，选择器与以前完全一样；没有被任何工作区包含的目录也一样。

## Alternatives considered

只匹配完全相同的注册路径被否决：在项目子目录里启动至少与在项目根启动一样常见，而分段规则让这件事保持安全。顺便自动打开最近的会话也被否决：读者要求跳过的是工作区这一问，不是会话这一问，悄悄恢复一段对话是更大的意外。为这条捷径加开关被否决——`cd` 就是开关，而 `←` 一键即可撤销。

## Consequences

`tests/ui/app.test.tsx` 新增一条：把客户端目录设为夹具注册的工作区路径后启动，断言屏幕是会话列表、选中 `w1`、帧里不再出现工作区选择器、并且状态行解释了原因；另一条断言无关目录仍停在选择器上，且匹配按分段进行（`/host/project/src/deep` 命中 `w1`，`/host/project-old` 不命中）。`tui-design.md` 的 2.6 / 4.1 / 7.2 与 README 双语记录了该行为。没有新增状态、没有新增依赖，远端宿主行为不变。
