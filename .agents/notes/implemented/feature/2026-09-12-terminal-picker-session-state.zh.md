# Agent Note: 选择器显示会话正在做什么

Status: implemented

## Problem

`/ws` 与 `/resume` 只用标题与标识符描述自己的行，唯一的活动信息是运行中会话标题前的一个 `●`。工作区行完全不提它的会话，于是要在两个工作区之间选择就必须各打开一次才能看出哪个有活在跑；而一个从未跑过回合的会话，与一个几小时前结束长对话的会话看起来一模一样。

## Decision

两个选择器都读取会话列表本来携带的状态，不加载任何会话历史。会话行以一个标记和最近活动时间开头：agent 在跑时是 `◐ 2m`，跑过回合之后是 `● 5m`，第一个回合之前是 `○`。工作区行以同样的标记开头、按该工作区名下的会话计数，运行中的排在最前，于是 `◐ 1  ● 1  ○ 1  Project α  /host/project` 在打开之前就回答了哪个工作区在忙。

`session/navigation.ts` 里的 `sessionState`、`SESSION_MARKERS`、`activityAge`、`sessionStatus` 与 `workspaceStatus` 持有这套分类，使两个选择器与它们的测试共用同一个定义。分类只读取宿主摘要里的 `running` 与 `blank`，从不从沉默推断停滞：时间取宿主的 `updatedAt`，没有活动时间的会话只显示标记。时间粒度保持粗糙——`now`、分、时、天——因此用户阅读时一行不会变动。

## Alternatives considered

对运行中但 `updatedAt` 已停止前进的会话推导「正在等待你」被否决，因为长时间工具运行与阻塞在提示上无法区分，而宿主没有发布能区分两者的信号：审批审计对（`approval/asked`、`approval/decided`）在会话日志里是持久的，但没有任何列表投影暴露它。显示该状态需要宿主侧的投影，属于另一处改动。把等待中的会话排到最前也因同样原因被否决。逐个读取会话尾部来检查同样被否决，因为读尾部需要 follow 该会话，等于订阅列表中的每一个会话。

## Consequences

`tests/session/navigation.test.ts` 覆盖分类、粗糙的时间粒度、负时长钳制与工作区计数。`tests/ui/app.test.tsx` 用固定列表渲染两个选择器，断言标记、时间与汇总。没有会话的工作区不显示标记而不是零计数，活动时间未知的会话只保留自己的标记。
