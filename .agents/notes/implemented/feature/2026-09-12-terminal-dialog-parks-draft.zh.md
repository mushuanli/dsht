# Agent Note: 要求回答的对话框会寄存草稿

Status: implemented

## Problem

审批请求或提问在宿主决定发问时到达，而这常常发生在一条消息写到一半的时候。对话框只在输入框为空时才接管数字键与方向键——输入框里有草稿被当作"用户正在打字而不是在回答"的证据——因此字段里残留一个字符就会让 `1`–`3`、`↑`、`↓` 完全失效、`Enter` 也确认不了任何东西。草稿并没有丢，但对话框已经无声地停止工作，唯一的线索是一行宣称可以输入命令的提示，而那个输入框已经被占用了。

## Decision

要求回答的对话框在解决之前接管键盘。它打开时，输入框里的内容被寄存：字段清空、提示符转暗、字段不再接收按键，于是对话框自己的快捷键立刻生效。最后一个待答交互清空后，被寄存的草稿写回，且直接写状态而不走 `setInput`——还原草稿既不是新消息也不是从历史召回，不能让读者的滚动位置移动。

提问在需要时保留输入框：纯文本提问、以及切到 `Other answer` 的提问都让字段保持活跃，答案仍然在一直以来输入答案的地方输入。只读而不需回答的面板——`/help`、`/cost`、`/status`、`/think`、`/history`、`/model`、各选择器——保持原有行为：字段保持活跃，而打开的面板在有草稿时拒绝选中。

## Alternatives considered

保留草稿并让对话框的按键优先于它被否决，因为可见结果同样是那种令人困惑的状态：用户看到自己并没有在输入的文字，而 `Enter` 随后既确认对话框、又提交字段里的内容。清空草稿而不保留它被直接否决：审批请求不能毁掉一条消息。让所有面板都寄存草稿被否决，因为一边读 `/help` 一边拼命令、以及用命令切换面板都很有用，而它们与回答并不争抢同一组按键。

## Consequences

`tests/ui/app.test.tsx` 先写入草稿、再触发审批，断言对话框打开时草稿消失，用一个数字作答，并断言请求解决后草稿回来——这一过程重复两次，因此"忘记还原"会被看见。原本把 `/allow` 与 `/deny` 打进字段的两个测试改为用对话框自己的列表作答，`tests/expected/approval-options.txt` 记录说明这一点的新提示行。自定义答案测试仍然把答案打进输入框，这正是纯文本路径保持被覆盖的原因。
