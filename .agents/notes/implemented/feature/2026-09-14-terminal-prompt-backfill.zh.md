# Agent Note：打开会话即折叠整段提示词历史

Status: implemented

## Problem

回填索引原先只由开屏跟随快照播种——宿主把它限制在最新 80 条记录——加上之后到达的增量。更早的提示词是**可达**的（边界处先从已加载窗口补回，再翻页），但并不在数组里。在长代理会话里，这意味着读者要按 ↑ 穿过一页页工具与助手记录才能到开头；而一次按键若扫完自己的页数配额仍没找到提示词，看起来就像按键坏了。读者在打开会话时期待的提示词列表属于整个会话，而不是那个窗口。

## Decision

`selectSession` 在订阅之后启动 `SessionController.backfillPrompts`。它从开屏窗口向前逐页走 `session/page`，把每页解析进一份临时 `Transcript`，只通过 `Transcript.promptsSince` 抽取 user prompt 并 `prepend`，直到宿主报告 `hasMore === false`。每份临时记录立即 `dispose`，因此实时记录、它的内存窗口与行缓存都不会增长——这次遍历只花网络与"提示词大小"的内存。它有 200 页上限，下一次选择或释放即取消，并吞掉取消、断线与历史不可用，把剩下的交给惰性回退路径。

当遍历因宿主回答"没有更早的了"而结束时，`PromptIndex.markComplete()` 记下索引已穷尽，`recallHasOlder` 此后不再提出一个只可能返回空结果的翻页请求；被页数上限截断时该标志保持未置位，惰性路径继续生效。完成的遍历还会调用 `PromptIndex.settle()`，把刚批量加入的条目裁剪回 2,000 条 / 512 KiB 预算；被裁掉的前缀仍可按需通过惰性路径取回，这与预算原本遵循的规则一致。

## Alternatives considered

复用计费扫描播种在这一步被否决：扫描归计费域所有、按定时器为每个会话运行，把它的分页流与会话索引关联起来会让计费与回填耦合，却没有用户可见的收益。只返回 `user/message` 页的宿主端点被列为超出本次范围，但它才是终态——它能消除"回填与计费扫描各自以 80 条/页读同一份日志"的重复。把遍历推迟到第一次边界按键被否决，因为读者要的是列表，不是在按键背后悄悄取一页。

## Consequences

`tests/ui/app.test.tsx` 新增一条：历史横跨四页，断言打开后索引立即按从旧到新持有全部 8 条提示词、走回第一条不花任何页请求、再多按一次是报告结尾而不是翻页。两条原先统计 `session/page` 次数的测试改为等待回填完成后断言增量，因为打开会话确实会读历史。`tui-design.md` 的 4.3 / 5.3 / 5.5 / 5.7 与附录记录了该变更，README 双语记录了后台遍历。
