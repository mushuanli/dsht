# Agent Note: 有界的运行时内存日志

Status: implemented

## Problem

长时间运行的终端会话会显示常驻内存上升，但客户端内部没有任何信息能说明这是真实保留的内容还是 V8 从不归还给操作系统的内存高水位。保留窗口、回看保护状态与账本规模只能通过调试器或测试脚手架观察，因此"内存一直涨"的报告无法从运行中的进程里得到解答。

## Decision

交互客户端默认在 `<state>/memory.log` 启用内存日志。它每 30 秒追加一行 JSON，包含进程计数（`rss`、`heapTotal`、`heapUsed`、`external`、`arrayBuffers`）、决定回收行为的控制器状态（`online`、`screen`、`session`、`pinned`、`pending`）、保留内容（`records`、`retainedBytes`、`beforeSeq`、`hasMore`、`live`），以及存在账本时的会话数、charge 数与未计价数。样本只含计数与大小：提示词、工具、思考或会话正文都不会写入该文件。

文件在结构上就是有界的。样本经 `storage.appendPrivateFile` 追加；累计追加达到 1,000 行时，用表头加最新 1,000 行原子重写文件，因此两次重写之间不会超过其两倍，也永不无界增长。写入失败会把原因记录在日志对象上、清除定时器并让客户端继续运行——诊断功能不能变成终端的故障源。

`--memory-log <路径>` 与 `DSHT_MEMORY_LOG` 可替换路径，`--no-memory-log` 与 `DSHT_MEMORY_LOG=off` 可关闭；`--memory-log` 传空值会在启动时直接失败，而不是静默回退到默认值。`list` 子命令从不打开它，库调用方在不传路径时也不会产生日志。

## Alternatives considered

定时调用 `global.gc()` 被否决：实测它只降低活堆，常驻内存仍停在高水位，因此只会增加 CPU 开销而不改善用户观察到的现象。用 `--max-old-space-size` 限制堆被否决作为默认做法，因为那会把诊断问题变成部署方应自行决定的调优选择。复用 WeakMap 缓存不适用：真正造成增长的是有意的保留（回看保护的窗口与账本历史），弱引用无法释放它们。写 stdout 被否决，因为会破坏 Ink 的画面。

## Consequences

README 配对文档记录了默认路径、选项、环境变量以及默认启用这一事实，设计文档在 CLI、存储与隐私三节记录了它。三项测试覆盖样本字段与文件权限、有界重写，以及不传路径与写入失败两种情况。代价是每 30 秒一次很小的追加、每个文件生命周期一次 1000 行重写；收益是增长报告可以通过读一个文件回答，而不必先复现它。
