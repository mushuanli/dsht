# Agent Note: 状态面板一屏放得下

Status: implemented

## Problem

展开的 `/status` 面板让好几个很短的值各占一行——主机、会话 ID、模式、回合数、排队数与活动任务都各带一个标签——并且把每个单位都写全。在 46 列下这需要 28 行，在手机上就是两屏，而这些行里大多数连一半宽度都没用满。面板确实可以滚动，但读者要为了本来放得下的信息去滚动。

## Decision

相关的值合到同一行，标签与单位改用短形式：连接状态与活动状态合成一行，会话 ID 后面直接跟模式，三行指标变成 `Context ~40% (400,644/1,000,000) · 229,270,604 tok` 与 `In 476,510 · Out 794,094 · Cache 228,000,000/0`，费用行带上回合数，于是排队数与任务数占用最后一行。错误仍然各自占行，因为它们只在出问题时出现，而它们的文本正是打开这个面板的原因。计数改用单行状态栏已经在用的紧凑形式——`Context ~40% (400.6K/1M) · 229.7M tok` 与 `In 476.5K · Out 794.1K · Cache 228.4M/0`——因为八位总数会把每一行指标在窄宽度下推到第二行。换行与滚动偏移都保留：值仍按终端宽度换行，容纳不下精简后内容的小终端仍然滚动而不是截断。

## Alternatives considered

删掉字段被否决，因为这些值正是面板存在的目的。用省略号缩短会话 ID 或工作区路径更早被否决，因为会丢掉读者可能需要复制的信息。宽终端上的双栏布局被否决，因为它对促成这次改动的窄终端毫无帮助，而宽终端本来就能容纳精简后的行。

## Consequences

实测：常见情况下 46 列需要 11 行、80 列需要 10 行；带较长会话 ID 与一条较长错误行时 46 列需要 14 行，而此前是 28 行内容。20 行终端在扣除表头与输入框后正好够用，24 行终端还有富余；12 行终端仍然滚动，因为这种尺寸下任何布局都放不下这些信息。`tests/expected/status-bar.txt` 与应用断言现在都指向精简后的行，`metricLines` 返回短标签并由其测试固定。
