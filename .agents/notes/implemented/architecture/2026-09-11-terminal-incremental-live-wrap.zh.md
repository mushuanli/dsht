# Agent Note: 实时尾部的增量换行

Status: implemented

## Problem

每次重建布局时，`historyLayout` 都会把每个实时部分整段重新换行，而每一帧流式输出都会触发重建。于是开销随累计回答长度与帧数的乘积增长：一段 36,000 字符、分 1,500 帧到达的回答，花在换行上的时间是 20.8 秒，而这些文本的靠前行早已不可能再变化。折叠的实时推理有同样的问题，只是规模更小——只显示一行，却要用整段推理文本构造那一行。

## Decision

实时部分现在带一个稳定的 `key`（`<attempt>:<block index>`），每个布局维护一张 `liveWraps` 表，把该 key 映射到 `{width, reasoning, kind, length, rows, carry}`。`rows` 保存文本已不可能再变化的行，`carry` 保存唯一仍会变化的那一行的原始来源；新到达的增量追加到 `carry`，只有这段剩余内容会重新换行。最后一个非空行之前的每一行都是最终行，因为文本只会增长，不会让它重新折行。

恢复 `carry` 需要该行在来源中的偏移量，而 `wrap-ansi` 会裁掉每一行两端的空白，所以渲染出的行并不是来源的连续切片。`rawStart` 从后向前匹配该行、跳过来源中的空白，并在有限的扫描步数后停止。匹配失败，或 `carry` 长于 `width * 4 + 64` 时，会退回到整段文本重新锚定；重新锚定失败则回到一次性换行，并且不写入任何状态。折叠用自己的 `foldedSource` 限制输入，它不断加长前缀，直到折叠行填满宽度。

`liveWraps` 随索引其余部分一起由 `dispose` 清空，因此这些状态不会比拥有它的布局活得更久。

## Alternatives considered

重写换行逻辑被否决，因为 `wrap-ansi` 掌握着这个终端已经在使用的硬换行、裁剪与东亚宽度规则。按文本缓存渲染结果被否决，因为每一帧都会产生新文本，缓存永远不会命中。当增量看起来无害时跳过换行被否决，因为无法证明输出相同。把整段文本留在状态里逐帧切片，保留了这次改动正是要避免的内存占用。

## Consequences

对每一个增量，渲染出的行都与整段换行完全一致。`tests/session/live-wrap.test.ts` 播放确定性的随机文本（包括纯空白与含换行的增量），在 16 到 100 的各种宽度上，每一帧后都把布局与一次性换行做比较；如果实时部分丢掉了增量路径所需的身份，测试立即失败。同一段实测流：整段换行 20.8 秒，增量换行 268 毫秒。保留的状态仍然有界，等于布局本就缓存的最终行加上一行 `carry`。
