# Agent Note: 有界的连接、屏幕与选中项迁移日志

Status: implemented

## Problem

客户端会由读者从未输入过的代码改变屏幕：重连会执行 `ready()`，它重新加载选择器，还可能采用本地工作区并重新解析已选会话。当这些迁移最终停在意料之外的位置时，进程内部没有任何信息说明是哪一次迁移造成的。内存日志确实记录了 `screen` 与 `session`，但那是每 30 秒一个的样本，因此它只显示跳转之后的状态而不是造成跳转的事件，也无法区分"读者按了 Escape"和"一次重连落在了选择器上"。促成这件事的具体报告是：客户端会在对话过程中时不时回到会话列表，也就是 `/resume` 打开的那个界面。

## Decision

交互客户端默认在 `<state>/trace.log` 启用有界的迁移日志。`TraceLog` 每行追加一个 JSON 事件，并在每个决策点记录：`generation` 事件（`begin`、`ready`、`ended`、`settled`）、请求的 `picker`、客户端目录与已注册工作区的 `adopt` 匹配结果、会话 `resolve`（含是否重新选中及原因），以及 UI 驱动的每个会改屏幕的入口所对应的 `action` 事件。此外，只要 `screen`、`sessionId`、`workspaceId` 或 `online` 发生变化，`Controller.update()` 就记录一个 `state` 事件，带上变化前后的取值（`"chat -> sessions"`、`"s1 -> none"`），因此没有对应原因事件的迁移仍然可见，而不会静默跳过。

文件在结构上就是有界的，且写入从不阻塞状态更新：`record()` 把本次追加串在上一次之后，累计追加达到 2,000 行时用表头加最新 2,000 行原子重写文件；写入失败会记录在日志对象上，客户端继续运行。事件只含标识与屏幕名，绝不包含提示词、工具、思考或会话正文。

`--trace <路径>` 与 `DSHT_TRACE` 可替换路径，`--no-trace` 与 `DSHT_TRACE=off` 可关闭；`--trace` 传空值会在启动时直接失败，而不是静默回退到默认值；库调用方在不传路径时不会产生日志。内存日志与迁移日志共用同一个路径解析器，避免两项诊断的语义各自漂移。

## Alternatives considered

把迁移列表挂进内存样本被否决：它仍然只在 30 秒的采样点写入，跳转前后的事件仍可能丢失，而且该样本已经带有布局、缓存与扫描计数，不适合被迫频繁采集。写 stderr 被否决，因为会破坏 Ink 的画面。记录每一次状态补丁被否决为噪声：只有当决定读者所见的那四个字段真正变化时，迁移日志才写入。把日志做成显式开启被否决，因为它要解释的报告是间歇性的，而"等下次复现再开"的诊断通常一直处于关闭状态。

## Consequences

加了迁移日志后，报告中的跳转无需调试器即可解释：在客户端正阅读会话时发生重连，`ready()` 仍会调用 `adoptLocalWorkspace`，因为它的守卫只排除了 `sessions` 界面，于是客户端目录被采用、`pickWorkspace` 清空选中项，`resolve` 事件记录 `session: "none", reselect: false`，其前是 `"workspaces -> sessions"` 与 `"s1 -> none"` 两条 `state` 事件。`ready()` 在捕获到的界面为 `chat` 时是否还应该执行采用，是一个独立的行为决策；无论结论如何，迁移日志都会记录这条链路。两项测试分别覆盖文件本身（表头、追加、私有权限、目录创建）与上述重连链路。`README.md`、`README.zh.md` 与设计文档的 CLI、存储与文件表记录了这些开关、默认值，以及"不写入任何消息正文"这一事实。
